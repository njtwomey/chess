# Recording availability

The captain asks the squad a fortnight before each fixture and gets back a
scatter of messages. This turns those into `availability` entries on one match.

## What you are editing

`content/seasons/<season>/matches.json`, the `availability` array of one match.
Nothing else. Never touch `result`, and never edit a player's game count: it is
counted from results and does not exist as a field.

```json
{ "playerId": "gwen-tsai", "reply": "yes", "at": "2026-09-04", "note": "Might be ten minutes late." }
```

`at` is the date they replied, which is what makes a past selection auditable.
`note` is optional and only for something the captain would otherwise have to
remember.

## Mapping what people write to the four replies

The four are fixed and the difference between them decides who plays.

| They wrote                                                              | reply     |
| ----------------------------------------------------------------------- | --------- |
| "I'm in", "yes", "count me in", "should be fine"                        | `yes`     |
| "I can reserve", "only if you're short", "happy to be back-up"          | `reserve` |
| "not sure", "depends on work", "provisionally yes", "I'll let you know" | `unsure`  |
| "can't make it", "away that week", "no"                                 | `no`      |

**"Provisionally yes" and "probably" are `unsure`, not `yes`.** A `yes` can be
put on a board without a further word, and that is the whole difference. When a
message could be read either way, record `unsure` and tell the captain you did
and why, so they can chase rather than discover it on the night.

## When somebody drops out

Someone who said yes or offered to reserve, and then pulls out, is **not** changed
to `no`. Add a `withdrawn` block and leave their reply alone:

```json
{
  "playerId": "mira-vance",
  "reply": "yes",
  "at": "2026-09-02",
  "withdrawn": { "at": "2026-09-14", "note": "Called away for work." }
}
```

This matters for two reasons. It keeps the record honest, because they were
available and were picked, and changing the reply would make the site say they
never offered. And it is what preserves the order: the site takes that one
person out of the list it already made and moves everybody below up one place,
so the first reserve takes the empty board. Rewriting the reply would re-run the
rule from scratch, which can re-decide a tie that was already settled and put
somebody on a board after they had been told they were not playing.

`withdrawn` on a reply of `unsure` or `no` is rejected by the loader, because you
cannot drop out of something you never offered to do.

## Settling the team

The board order is computed from the moment four people are picked, but it is
**not shown** until the match says so:

```json
"settled": true
```

Leave it off while the replies are still arriving. A running order shared
mid-week is one that is going to change, and the point of sharing a match early
is to show who has replied, not to publish a lineup. Until it is settled the
page shows the replies alone: no position, no outcome, no reasoning. A played
match is settled automatically.

## How to do it

1. Ask which match if it is not obvious. Match ids look like `demo-r5`.
2. Match each name to a `playerId` from that season's `players.json`. Never
   invent a player to fit a message. A name you cannot place is something to ask
   about, and the answer might be that they need adding first.
3. One entry per player. If somebody has replied before, **update their existing
   entry** rather than adding a second: two replies from one player is a data
   error and the site will refuse to load.
4. Leave people who have not replied out entirely. Silence is not `unsure`; the
   site already shows non-repliers as still to hear from, and inventing a reply
   for them would say they answered when they did not.
5. Run `make check`. The loader validates ids and duplicates.
6. Report back: how many of each reply, who the rule now picks, who moved up if
   anybody dropped out, and who is still silent. Point at `/match/<id>` for the
   working.

## Afterwards

Offer the captain the "Copy for the group chat" text from the match page, which
is generated by the same function that made the selection. Do not write your own
summary of who is playing; it will drift from the rule.
